# Spec — Issue #4: Add deleteBuild method to API service

**Type:** feature

> Generated by Tsukinome. This file is the source of truth for the work; edits here drive the build.

## Summary

Add a deleteBuild(buildId: string) method to the frontend ApiService that issues an HTTP DELETE request to the existing /api/builds/:id endpoint, following the same patterns and return types as existing methods such as getBuild and query.

## Requirements

Each requirement is tagged with a confidence level (explicit / inferred / assumption / unknown).

- **R1** `[explicit]` ApiService exposes a public method named deleteBuild that accepts a single string parameter buildId.
- **R2** `[explicit]` Calling deleteBuild(id) issues an HTTP DELETE request to the URL ${API_BASE}/api/builds/${id}.
- **R3** `[explicit]` deleteBuild returns the HttpClient observable (does not subscribe internally), consistent with getBuild and query.
- **R4** `[explicit]` The method's style, typing, and return-type conventions mirror existing methods like getBuild and query.
- **R5** `[assumption]` The generic/return type of the observable matches whatever the DELETE response body is (e.g. void or a build object), consistent with existing method conventions.

## Acceptance Criteria

### AC1

- **Given** A valid build id string
- **When** deleteBuild(id) is called
- **Then** An HTTP DELETE request is sent to ${API_BASE}/api/builds/${id}.

### AC2

- **Given** deleteBuild is invoked
- **When** the method returns
- **Then** It returns the HttpClient observable without subscribing, matching the pattern of getBuild and query.

### AC3

- **Given** A build id containing characters requiring encoding
- **When** deleteBuild(id) is called
- **Then** The request URL is constructed consistently with how existing methods build their URLs.

## Non-Goals

- No UI or button changes.
- No backend endpoint work; only the frontend service method is added.

## Edge Cases

- Empty or whitespace-only build id.
- Build id containing URL-special characters requiring encoding.
- Server responds with an error (e.g. 404 or 500) — error propagation should match existing methods.

## Assumptions

- The DELETE response body type and observable generic follow the conventions of existing methods; the exact return type (void vs. build object) matches what the backend returns and is consistent with existing patterns.
- URL construction (including any encoding) mirrors existing methods rather than introducing new handling.
